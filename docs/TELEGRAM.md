# Уведомления в Telegram

На сервере коллектора можно включить Telegram-мониторинг через пункт **Настроить Telegram**. Монитор проверяет только выбранные события и отправляет отдельную карточку на каждую проблему. После восстановления он обновляет исходное сообщение и добавляет время окончания. Если исходное сообщение удалили или его нельзя изменить, монитор отправит отдельное тихое сообщение.

## Настройте монитор на коллекторе

Выполните команды из версии исходников, в которой есть каталог `collector/notify/`. Если ваш клон закреплён на теге v1.3.0, возьмите отдельную копию актуального `main` для настройки уведомлений. Для этого не нужно переустанавливать коллектор.

1. Создайте бота, добавьте его в служебный чат и выдайте право отправлять сообщения. Подготовьте числовой ID чата и, если используете тему форума, её ID.
2. Выполните `sudo bash install.sh --lang ru notify`. Укажите токен, чат и номера проверок через запятую. Токен вводится без отображения и хранится на коллекторе в файле `/opt/logcollector/notify/config.json` с правами `0600`.
3. Проверьте список включённых проверок командой `sudo bash install.sh --lang ru notify status`. Команда `sudo bash install.sh --lang ru notify test` отправляет одно тестовое сообщение в указанный чат.

| Проверка | Когда появляется тревога |
| --- | --- |
| Сервисы коллектора | Loki или Grafana не отвечают, либо контейнер Vector остановлен. |
| Доставка по нодам | У выбранной ноды нет контрольных записей в Loki за 5 минут. Заранее [включите таймер записи](LOG-DELIVERY.md) и убедитесь, что Loki видит метку ноды. |
| Диск | Файловая система с очередью архива заполнена на 90% или больше. |
| Архив | Таймер остановлен, последняя задача завершилась с ошибкой или превысила установленный срок без успешного запуска. Укажите срок больше интервала таймера. Успешный запуск может завершиться без новых файлов. |
| `error.log` | На ноде больше 20 строк за скользящие 5 минут и превышение держится 5 минут. |
| Свежесть Xray | От выбранной ноды нет обычных записей за 15 минут. Нода может быть доступна и просто не обслуживать трафик. |

Монитор запускается раз в минуту. Для остальных тревог нужна подтверждённая проблема в течение двух минут. Если Loki не выполнил запрос, монитор сообщает об ошибке запроса и приостанавливает оценку этого сигнала по нодам. Пропажа серии `error.log` сама по себе не закрывает тревогу.

В сообщениях есть метки нод, названия проверок и время UTC. Сырые строки логов, IP клиентов и данные аккаунтов не отправляются. Если Telegram принял запрос, но ответ потерялся, повторная доставка может создать второе сообщение.

Для изменения настроек снова запустите `notify`. Команда `sudo bash install.sh --lang ru notify disable` останавливает локальный монитор. Приём Beszel и внешний watchdog имеют свои команды остановки.

## Проверьте коллектор с другого сервера

Watchdog работает на отдельном Linux-сервере, например на сервере панели. Коллектор раз в минуту отправляет SSH-сигнал. Если приёмник ничего не получил за три минуты, watchdog сообщает об этом в Telegram. Эта тревога означает, что сигнал перестал доходить. Возможные причины — остановка коллектора, таймера или проблемы на сетевом пути. Для восстановления watchdog ждёт новые сигналы. Дополнительно можно указать HTTPS-адрес Beszel и проверять с этого сервера `/api/health`.

### Подготовьте приёмник и ключ

На **коллекторе** создайте отдельный SSH-ключ для автоматической отправки сигнала.

```bash
sudo ssh-keygen -t ed25519 -N '' -f /root/.ssh/log-service-heartbeat
```

На **сервере watchdog** заведите отдельного пользователя и выделите ему каталог только для записи сигнала. Команды рассчитаны на новую настройку.

```bash
sudo useradd --system --home-dir /var/lib/log-service-heartbeat --shell /bin/sh logsvc-heartbeat
sudo install -d -o root -g root -m 0755 /var/lib/log-service-heartbeat
sudo install -d -o root -g root -m 0755 /var/lib/log-service-heartbeat/.ssh
sudo install -d -o logsvc-heartbeat -g "$(id -gn logsvc-heartbeat)" -m 0700 /var/lib/log-service-heartbeat/inbox
sudoedit /var/lib/log-service-heartbeat/.ssh/authorized_keys
```

Добавьте одну строку. Замените `COLLECTOR_IP` адресом коллектора, который видит SSH-сервер, и подставьте открытый ключ из файла `log-service-heartbeat.pub`.

```text
from="COLLECTOR_IP",restrict,command="/opt/log-service-watchdog/receive-heartbeat.sh" ssh-ed25519 PUBLIC_KEY
```

Файл `authorized_keys` должен принадлежать root и читаться выделенным пользователем, например с правами `0644`. Параметр `restrict` отключает интерактивный терминал и перенаправления. Принудительная команда записывает только время приёма сигнала. У пользователя должны быть разрешены вход по ключу и выполнение этой команды в вашей конфигурации SSH.

### Соедините серверы

На **коллекторе** запишите в `/etc/log-service-heartbeat-ssh.conf` параметры соединения. Замените `WATCHDOG_HOST` адресом второго сервера. В `/root/.ssh/log-service-watchdog-known_hosts` положите ключ его SSH-хоста, предварительно сверив отпечаток по доверенному каналу.

```sshconfig
Host log-service-watchdog
    HostName WATCHDOG_HOST
    User logsvc-heartbeat
    IdentityFile /root/.ssh/log-service-heartbeat
    IdentitiesOnly yes
    UserKnownHostsFile /root/.ssh/log-service-watchdog-known_hosts
```

На **сервере watchdog** запустите `sudo bash install.sh --lang ru notify watchdog`, укажите получателя и, при необходимости, HTTPS-адрес Beszel. Затем на **коллекторе** выполните `sudo bash install.sh --lang ru notify heartbeat`. Установщик проверит первую отправку и запустит таймер. На втором сервере проверьте, что метка обновляется.

```bash
sudo stat /var/lib/log-service-heartbeat/inbox/received
sudo systemctl status log-service-watchdog.timer
```

На тестовом контуре остановите таймер отправки и проверьте тревогу. Верните таймер и дождитесь обновления карточки. Для отключения используйте `notify watchdog-disable` на втором сервере и `notify heartbeat-disable` на коллекторе.

## Подключите события Beszel

1. На коллекторе настройте Telegram через `notify`, затем выполните `sudo bash install.sh --lang ru notify beszel`. Укажите локальный или частный IPv4, по которому Beszel может достичь коллектора. Для Beszel в Docker это обычно адрес шлюза его сети. Ограничьте вход на TCP/7077 адресом Beszel. Для связи между серверами используйте закрытую сеть или туннель.
2. Выполните `sudo bash install.sh --lang ru notify beszel-url`. Скопируйте полученный URL в **Settings → Notifications** в Beszel. URL содержит ключ доступа. Храните его как секрет.
3. В таблице систем Beszel включите алерты **Status** и **Disk**. Используйте уникальные имена систем. Для связи поддерживаются события отключения и восстановления агента, для диска — превышение порога и возврат ниже порога. Пороги настраиваются в Beszel.

Приёмник сохраняет полученные события на диск перед ответом Beszel. Если Telegram временно не отвечает, очередь сохраняется. К одному событию подключения или заполнения диска привязана исходная карточка для каждой системы. При включённой проверке сервисов монитор также сигнализирует, если приёмник не отвечает или очередь не отправляется дольше двух минут.

Карточку о потере связи с агентом можно дополнить свежим результатом проверки через VPN. Для этого настройте [сквозные VPN-проверки Statusboard](../statusboard/README.ru.md) и добавьте в `/opt/logcollector/notify/beszel.json` поле `"probe_routes": {"demo-node": "demo-route"}`. Ключ — имя системы Beszel, значение — ID маршрута из кэша `/var/lib/remnawave-statusboard-v2/vpn-probes.json`. Монитор использует результат сквозного запроса младше трёх минут. Если свежей проверки нет, карточка об этом сообщает.

Для отключения удалите webhook в Beszel и выполните `sudo bash install.sh --lang ru notify beszel-disable`. Очередь и состояние остаются на диске. [Generic webhook в Beszel](https://beszel.dev/guide/notifications/generic)

## Настройте оповещения о всплесках в Grafana

Grafana также может отправлять сообщения о всплеске строк в `error.log` Xray. Правило и получатель создаются в интерфейсе Grafana. Чтобы не получать две тревоги на одно событие, включайте проверку `error.log` в одном из двух мест.

Для пропусков контрольных записей используйте [внешний мониторинг доставки](LOG-DELIVERY.md).

## Подключение чата

1. Откройте Grafana через SSH-туннель, как описано в [инструкции установки](INSTALLATION.md). Подготовьте бота с доступом к служебному чату. Можно использовать тот же чат, в который приходит мониторинг хостов.
2. В **Alerting → Notification configuration → Contact points** создайте контакт `Log Service Telegram` типа **Telegram**. Введите токен и chat ID в Grafana. Для темы форума укажите её ID в **Message Thread ID**. В **Parse Mode** выберите **None**, оставьте уведомления о завершении включёнными.
3. Вставьте в поле **Message** этот шаблон. Он выводит состояние и метку ноды из Loki. Сырые строки, адреса подключений и пользовательские идентификаторы в уведомление не попадают.

```gotemplate
Remnawave Log Service
{{ range .Alerts -}}
{{ if eq (index .Labels "alertname") "DatasourceError" -}}
Loki — ошибка выполнения запроса ({{ .Status }})
{{ else if index .Labels "node" -}}
{{ index .Labels "node" }} — {{ if eq .Status "firing" }}всплеск строк в error.log{{ else if eq (index .Annotations "grafana_state_reason") "MissingSeries" }}серия пропала, проверьте доставку логов{{ else }}порог больше не срабатывает, проверьте свежесть логов{{ end }}
{{ else -}}
Проверка уведомлений — {{ .Status }}
{{ end -}}
{{ end -}}
```

4. Нажмите **Test** и проверьте доставку в нужный чат или тему. Сохраните контакт. Токен храните в Grafana, исключите его из файлов проекта и экспортов для общего доступа.

## Правило для всплеска строк

Создайте **Grafana-managed alert rule** с именем `Xray error.log volume`. Выберите Loki, режим **Code**, тип запроса **Instant** и окно запроса 10 минут. Вставьте в запрос A:

```logql
sum by (node) (count_over_time({service="xray",stream="error"}[5m]))
or on (node)
(0 * sum by (node) (count_over_time({service="xray",stream="access"}[10m])))
```

Вторая часть возвращает ноль для нод со свежими access-записями, когда в error-потоке нет строк. Если исчезли оба потока, серия ноды может пропасть. Свежесть доставки требует отдельной проверки.

| Настройка | Значение для пилота |
| --- | --- |
| Условие | **Threshold** для A, **Is above** `20`, назначить условием оповещения |
| Evaluation interval | 1 минута |
| Pending period | 5 минут |
| Keep firing for | 0 минут |
| No data | **Normal** для этого правила |
| Execution error or timeout | **Error**, создаёт отдельный `DatasourceError` |
| Contact point | Выбрать `Log Service Telegram` напрямую |
| Group by | `alertname`, `node` |

Если редактор добавил **Reduce** автоматически, можно оставить **Last** и применить **Threshold** к его результату. Сохраните правило после проверки, что предварительный просмотр возвращает отдельную серию на ноду. Порог 20 — стартовое значение для стенда. Для рабочего парка подберите порог по истории конкретных нод и уровню логирования Xray. Метка `stream="error"` обозначает файл, поэтому в него могут попадать строки разных уровней важности.

## Проверка пилота

- На изолированном стенде с отдельным чатом отправьте синтетические access-записи с двух разных нод. На одной поддерживайте больше 20 строк в error-потоке за скользящие 5 минут. После 5 минут превышения и задержки группировки сообщение должно содержать только ноду с превышением.
- Остановите тестовые error-записи, продолжив access-поток. Проверьте переход через порог и уведомление о завершении.
- Для проверки `MissingSeries` временно поставьте **Pending period** в ноль на стенде. Отправьте одной пачкой больше 20 error-записей для тестовой ноды без access-записей за последние 10 минут. Продолжайте access-поток второй ноды. Когда пачка выйдет из окна 5 минут, первая серия исчезнет, а сообщение о завершении должно явно указать пропажу серии. После проверки верните **Pending period** к 5 минутам.
- На стенде сделайте Loki недоступным при работающей Grafana. Проверьте отдельное сообщение об ошибке запроса и его завершение после восстановления Loki.
- Чтобы остановить пилот, приостановите правило. Для полного удаления сначала удалите правило, затем контакт. Правило и контакт сохраняются в данных Grafana, поэтому при переносе учтите том `grafana-data`.

Внешний мониторинг нужен для обнаружения недоступности самой Grafana, пропажи потока отдельной ноды и отставания архива. Эти события требуют отдельных правил и не выводятся из количества строк в `error.log`.

Документация Grafana: [Loki Alerting](https://grafana.com/docs/grafana/latest/datasources/loki/alerting/), [Telegram](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-telegram/), [No Data и Error](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/nodata-and-error-states/).
